# Pairadox

## Краткое описание

Pairadox — интерфейс для поддержки закупочных решений. Проект помогает менеджеру по закупкам понять, какие товары требуют пополнения, почему система предлагает определённое количество и какие исходные данные влияют на это решение.

Главная идея проекта — сделать рекомендацию по закупке проверяемой и объяснимой, а не показывать только итоговое число.

## Проблема

История продаж может содержать сезонные изменения, рост спроса, пропуски, отрицательные значения, незавершённые периоды, зарезервированный товар и крупные повторяющиеся заказы. Если использовать такие данные без проверки, прогноз может привести к лишнему запасу или дефициту.

Pairadox объединяет историю продаж, остатки, резерв, товары в пути и ограничения по кратности заказа в одном интерфейсе. Пользователь может посмотреть исходную динамику и разобрать логику рекомендации по конкретному товару.

## Основные возможности

- таблица рекомендаций по товарам;
- фильтрация по поставщику IEK или Systeme Electric;
- поиск по названию, коду товара и поставщику;
- отдельная панель с объяснением расчёта;
- отображение остатка, резерва, свободного остатка и ожидаемых поставок;
- учёт единиц измерения товара;
- учёт кратности заказа;
- график месячной истории продаж;
- переключатели сценариев сезонности, роста и компенсации stockout;
- раздел контроля качества исходных данных;
- экспорт текущего демонстрационного представления в CSV;
- состояния загрузки, ошибки и отсутствия результатов.

## Как работает решение

Текущий frontend загружает демонстрационный набор продуктов и отображает его в React-интерфейсе. История продаж для шести примеров взята из предоставленных Excel-файлов IEK и Systeme Electric. Пустые значения истории сохраняются как пропуски и не превращаются автоматически в ноль.

После подключения backend пользовательский сценарий будет выглядеть так:

1. Пользователь открывает рабочее пространство закупок.
2. Выбирает поставщика или ищет товар.
3. Открывает строку товара в таблице рекомендаций.
4. Видит прогноз, остаток, резерв, товар в пути, safety stock и кратность заказа.
5. Проверяет объяснение рекомендации и историю продаж.
6. При необходимости сравнивает сценарии с разными предположениями.
7. Экспортирует подготовленные данные для дальнейшей работы.

## Технологии

- React;

## Установка и запуск

Требования:

- Node.js;
- npm;
- Git.

Клонирование проекта:

```bash
git clone https://github.com/BAITC-Hacks/hack-866564aa-pairadox.git
cd hackathon_alemai
```

Переход на frontend-ветку:

```bash
git checkout ingkar-frontend
```

Установка зависимостей и запуск frontend:

```bash
cd frontend
npm install
npm run dev
```

После запуска Vite покажет локальный адрес, обычно `http://localhost:5173`.

Проверка production-сборки:

```bash
npm run build
```

Проверка lint:

```bash
npm run lint
```

## Как проверить решение

Для демонстрации можно повторить следующий сценарий:

1. Открыть раздел `Overview`.
2. Нажать `Recommendations`.
3. Переключить фильтр `IEK` или `Systeme Electric`.
4. Выбрать товар в таблице.
5. Проверить панель объяснения справа.
6. Переключить `Seasonality`, `Growth trend` или `Stockout correction`.
7. Открыть раздел `Sales history` и выбрать другой товар.
8. Открыть раздел `Data quality` и показать ограничения исходных данных.
9. При необходимости нажать `Export demo CSV`.

## Данные и интеграция

В архиве IEK доступны:

- месячные продажи;
- месячные остатки;
- динамика продаж с датами документов;
- MOQ;
- товары в пути;
- сезонность.

В архиве Systeme Electric доступны:

- месячные продажи;
- месячные остатки;
- динамика продаж с датами документов;
- MOQ/кратность;
- товары в пути с остатком, резервом и свободным остатком;
- сезонность.

Источники используют разные структуры, поэтому перед объединением требуется нормализация по коду товара, единице измерения, датам и правилам заказа.

На момент написания README финальные backend endpoint-ы и формат ответа ещё не утверждены. После интеграции здесь нужно добавить:

- адрес backend;
- список endpoint-ов;
- пример реального JSON-ответа;
- правила расчёта прогноза и рекомендации;
- настройки CORS;
- команды запуска backend.

## Ограничения текущей версии

- рекомендации, forecast, priority и сценарные поправки в текущем frontend являются демонстрационными;
- frontend ещё не подключён к backend;
- customer ID отсутствует в предоставленной динамике продаж, поэтому customer-level anomaly analysis не заявляется;
- IEK monthly stock представлен как opening balance, поэтому его нельзя автоматически трактовать как текущий остаток;
- в некоторых источниках есть пустые значения и отрицательные количества;
- в данных Systeme Electric обнаружены расхождения по кратности заказа;
- в одном расчётном листе Systeme Electric период «последние 12 месяцев» требует дополнительной проверки, так как включает 13 месячных колонок;
- прогнозную точность нельзя оценить до появления backend-расчётов и тестового набора;
- ссылка на deployed-версию пока отсутствует.
